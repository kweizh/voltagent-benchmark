I have fixed the workflow type inference bug in `createWorkflowChain` where result schemas were not strictly enforced in complex branching scenarios.

### Changes made:

1.  **Strict Type Enforcement**: Updated the terminal methods of the `WorkflowChain` class (`toWorkflow`, `run`, `stream`, `startAsync`, `timeTravel`, `timeTravelStream`, `restart`, and `restartAllActive`) to use a TypeScript `this` parameter constraint.
2.  **Improved Error Messages**: When the data type at the end of a workflow chain does not match the expected `result` schema defined in `createWorkflowChain`, the compiler now produces a clear error message. The error message includes the expected schema type and the actual data type found in the chain.
3.  **Union Type Support**: The fix correctly handles complex branching (e.g., using `andWhen`) by ensuring that all possible branches in the resulting union type are assignable to the workflow's result schema.
4.  **Verified with Tests**: Added new test cases to `packages/core/src/workflow/chain.spec-d.ts` that specifically verify:
    *   Enforcement of result schema in a basic linear chain.
    *   Enforcement of result schema in a branching chain where one branch (or the default fall-through) does not match the expected schema.
    *   Updated existing tests to reflect the new strict enforcement.

### Verification:

Ran `pnpm run typecheck` in the `packages/core` directory. The TypeScript compiler now correctly identifies type mismatches in the workflow chain and flags them as errors, which was previously ignored. All existing and new tests pass the type check (verified by the fact that `@ts-expect-error` directives are now correctly consumed).

The fix is non-breaking for existing correctly-typed workflows but will catch previously silent type errors in user code.
